# 第 6 章 规模化:业务中台的 MCP 化

> 本章为全书差异化核心:方法论是本书立场(综合第 2/3/5/8 章的协议事实与中台工程常识);引用的外部产品形态标注[待核实]。

前两章的手艺都是"单个工具"级别的。现在放大尺度:业务中台有**数千个 REST 接口**,每个 Agent 项目都在重复封装。本章回答那个最常被问错的问题——

> "数千个接口怎么通过 MCP 暴露?"

**错误答案:暴露数千个工具。** 模型的工具选择准确率随工具数下降;每个工具的 schema 都占上下文;目录维护成本线性上涨。正确答案是一条工程化路径:**聚合、生成、拆分、检索、治理**。展开之前,先把协议给规模化准备的"地基"盘出来——这些不是我们的发明,是 2026-07-28 规范内建的能力。

## 6.1 协议为规模化准备的四块地基

| 协议能力(规范原文) | 规模化用途 | 详见 |
| --- | --- | --- |
| 工具集**随请求授权变化**(per-request 凭据) | 多租户可见性:租户 A 的 token 只看到租户 A 的工具——协议原生语义 | 第 8.4 |
| `tools/list` 的 `ttlMs` + `cacheScope` + 确定性排序 | 目录分发靠缓存,网关可共享缓存(`cacheScope: public`) | 第 3.2 |
| `server/discover` 一次拿到版本+能力+身份+`instructions` | 网关与消费端的接入握手点;`instructions` 是域的"自我介绍" | 第 2.6 |
| `subscriptions/listen`(toolsListChanged)+ `tools/list_changed` 通知 | 目录是活的:域上线新工具,消费端收到通知刷新 | 第 2.4 |
| `x-mcp-header`(参数 → `Mcp-Param-*` 头) | Gateway 不解析 body 按参数路由/限流/审计 | 第 5.7 |
| 显式句柄模式(Stateful Tools) | 跨调用状态(购物车/工单流程)不靠会话,靠参数传递的句柄 | 第 5.6 |
| 工具名唯一性 scope = 单 Server | 聚合层的消歧策略是必需品,`serverInfo.name` 不可依赖 | 第 5.1 |

一句话:**2026-07-28 的无状态重构,本质上是把 MCP 从"两端的会话协议"改造成"可被基础设施承载的分布式协议"**——没有这版,本章的拓扑会重得多。

## 6.2 接口 ≠ 工具:任务粒度聚合

中台接口按**系统资源**切(REST CRUD),Agent 需要按**任务语义**的工具。两者的翻译有四种模式:

| 模式 | 何时用 | 例子(贯穿案例) |
| --- | --- | --- |
| N 接口 → 1 工具(纵向聚合) | 一个用户任务背后固定的一串调用 | `after_sales_create_ticket` = 校验 + 风控 + 创建——原子任务不拆给模型,Server 侧编排 |
| 1 接口 → 1 工具(直通) | 接口本身就是完整任务语义 | `after_sales_query_ticket` |
| 1 接口 → 不暴露(裁剪) | 纯系统内部接口 | 批量对账导入、缓存刷新 |
| M 接口 → 1 工具 + 参数(归并) | 同一任务的变体接口 | 按 region/渠道拆的 4 个查询接口 → 1 个带 `region` 参数的工具 |

判定口诀:**模型需要"决定"的才做成参数;模型不需要知道的都收进 Server**。工具数量由任务词汇表决定(一个业务域通常 5-15 个任务),不由接口数决定——数千接口的各业务域,落下来是**每域个位数的工具**。

## 6.3 自动化生成管线:OpenAPI 是起跑线

手工写几千个工具不现实,中台都有 OpenAPI/Swagger 资产——管线让它变成起点而非终点:

```
OpenAPI 文档(资产)
   │ ① 解析:操作、参数 schema、描述 → 候选工具清单(自动)
   ▼
候选清单
   │ ② 人工评审:聚合分组(6.2)/裁剪/命名归一(domain_action)
   ▼
工具定义
   │ ③ 描述精修:任务语义重写、边界声明、格式示例(第 5 章标准)
   ▼
注册进域 Server(tools/list 确定性排序 + ttlMs/cacheScope)
```

三个工程要点:

1. **生成的是候选,不是成品**。schema 可自动,description 的任务语义重写是人工环节——省掉它的团队会得到"数量达标、模型不爱用"的工具集
2. **管线幂等可重跑**:OpenAPI 变更 → 重新生成 → diff 出"受影响工具清单"——同时是 6.5 变更管理的输入
3. **绑定消费端验证**:生成后立刻用真实 Agent 冒烟(第 7 章),命中率不达标打回精修

## 6.4 域拆分 + Gateway:拓扑

```
                ┌───────────────────────────────┐
  Host(Agent)──▶│         MCP Gateway           │
                │ 鉴权(CIMD)/租户 scope/限流/审计 │
                │ tools/list 聚合 + 缓存(ttlMs)  │
                └─┬─────────┬─────────┬─────────┘
             ┌────▼───┐ ┌───▼────┐ ┌──▼──────┐
             │售后域   │ │物流域   │ │商品域    │   ← header 路由分派
             │Server  │ │Server  │ │Server   │      每域独立迭代部署
             └────────┘ └────────┘ └─────────┘
                   ▼ 中台 REST 接口群
```

- **按业务域拆 Server**:域 = 迭代与责任边界(对齐组织结构),故障隔离,目录清晰
- **Gateway 是治理点**:统一鉴权(CIMD 消费端身份,第 8 章)、租户 scope 过滤(`tools/list` 随 token 变化)、限流审计(`Mcp-Name`/`Mcp-Param-*` 头免解析 body)、目录聚合缓存(`cacheScope: public` 时共享缓存可用)、legacy 兼容收敛(Dual-era 收口一处,第 3 章)
- 2026-07-28 之前,这层需要会话亲和、重放缓冲;**无状态 + header 路由之后,Gateway 第一次"薄得起来"**——托管网关产品(AWS AgentCore Gateway 等)[待核实:动笔时以市场现况为准]
- **命名消歧**:多域聚合后必然撞名(两个域都有 `search`),协议明确说聚合层要加前缀消歧、且不能依赖 `serverInfo.name`——所以域前缀(`after_sales_`)从第一天就是强制的

## 6.5 工具检索与动态发现:过载的最终解

域内工具数控制住了,Host 挂多域后总数仍会涨。分层解法,按需启用:

1. **按角色挂载**:客服 Agent 只挂售后+物流域。目录治理给"角色 → 域"映射——成本最低,优先做
2. **缓存式目录**:`ttlMs` 内直接用缓存目录;`cacheScope: public` 让网关层共享缓存——目录分发的正统机制,不用自建
3. **分页**:`tools/list` 游标分页,按"目录页"拉取
4. **search + load 模式**:工具真正巨大时,暴露 `search_tools` 元工具——模型先按任务描述搜、对选中的再 `load` 详情后调用。上下文里只有 1 个工具,背后是全部目录。行业实践(Anthropic 的 tool search 等)[待核实:以官方文档为准]
5. **活的目录**:域上线新工具 → `subscriptions/listen`(toolsListChanged)通知 → 消费端刷新。目录运营是日常,不是发版事件

## 6.6 目录治理:让规模化可持续

- **命名规范全域强制**:`domain_action`,域前缀即路由与消歧(6.4)
- **工具目录**:每工具一行——域、负责人、聚合接口清单、版本、状态(live/deprecated)。没有它,半年后没人敢动任何工具
- **变更管理**:描述/schema 修改走评审(直接改变模型行为);**破坏性变更新增工具名而非原地改**(工具名即 API);OpenAPI diff(6.3)驱动影响面
- **质量例行化**:命中率/失败率/重试率(5.6)月报;垫底工具走"精修或下线"
- **弃用对齐协议生命周期**:协议本身有 Active/Deprecated/Removed 政策(12 个月窗口,第 3 章)——工具目录同样标注弃用状态,给消费端迁移窗口

## 6.7 贯穿案例完整复盘

| 步骤 | 动作 | 产出 |
| --- | --- | --- |
| ① 输入 | 售后域 OpenAPI(20 接口) | 候选清单 |
| ② 聚合评审 | 任务词汇表讨论 | **6 个任务级工具**;3 接口裁剪;8 接口纵向聚合 |
| ③ 生成+精修 | 管线生成 schema;描述逐个任务语义重写 | 工具定义 + 目录条目 |
| ④ 域 Server | 实现(句柄模式处理撤销流程;`instructions` 写清域职责与边界) | `after-sales` 域上线,`ttlMs` 缓存就绪 |
| ⑤ Gateway 纳管 | 域前缀消歧;租户 scope 过滤;`Mcp-Name` 限流 | 多域拓扑一员 |
| ⑥ 消费验证 | agentscope-java + TS Client 双端冒烟(第 7 章) | 命中率达标,发布 |

20 接口 → 6 工具,压缩比 3:1 起步,且每个工具都是模型能准确选中的粒度。套到物流域、商品域,就是数千接口的全部真相。

## 6.8 小结

- 协议已经为规模化备好地基(授权化目录/缓存/discover/订阅通知/header 路由/句柄/消歧规则)——用好它们,别自建
- 工具数由任务词汇表决定;聚合、裁剪、归并是常态
- OpenAPI 管线生成候选,描述精修是人工质量关
- 域 Server + 薄 Gateway;过载解法分层上(角色挂载 → 缓存 → 分页 → search+load)
- 目录治理四件套 + 协议生命周期对齐

→ **第 7 章**把多域拓扑接上真实的异构消费端。
