# 第 5 章 工具接入实战

> **初稿状态(2026-10-24)**:代码行为在 TS SDK v2.4.0 实测(结构化输出、isError 路径);方法论部分为本书立场,发布前对照 spec server/tools 复核字段级细节。

第 4 章我们把链路跑通了;这一章解决的是另一层问题——**模型爱不爱用你的工具、用得对不对、出错后能不能自己爬起来**。同一个业务接口,工具建模的优劣可以让 Agent 成功率差出一个数量级。全书分量最重的两章之一,值得慢读。

贯穿案例继续:售后域 Server 从 echo 占位,长出第一批真实工具。

## 5.1 参数 schema:模型眼里的工具长什么样

模型看到的工具,就是 `tools/list` 返回的那段 JSON Schema。四条设计规则:

1. **类型最小化**:能用 `string` + 枚举描述的不造嵌套对象。模型对深层嵌套的填参错误率显著高于扁平结构。
2. **必填慎用**:每个 required 字段都是模型可能"编一个值"的诱惑。无法从上下文推断的参数,宁可做成可选 + 缺省语义,或用第 2 章 MRTR 的 `input_required` 向用户要。
3. **约束写进 schema**:格式约束(正则、枚举、范围)放 schema 约束里,不要只写在 description 里——schema 约束会被校验层执行,description 只是"劝说"。
4. **每个字段都有 `description`**:zod 的 `.describe()` 会原样进入 JSON Schema(第 4 章实测),这是成本最低、收益最大的投入。

```typescript
// 实测于 v2.4.0:约束与描述都进 schema
inputSchema: z.object({
  ticket_id: z.string()
    .regex(/^T-\d{4}-\d+$/, "格式 T-YYYY-NNNN")
    .describe("售后单号,如 T-2026-1031"),
  channel: z.enum(["app", "web", "miniprogram"])
    .describe("用户反馈来源渠道,未知时留空"),
}).partial({ channel: true }),  // channel 可选
```

## 5.2 描述质量:模型靠 description 选工具

工具选择的本质是**模型拿用户意图与工具描述做匹配**。同一能力,两种写法的成败差异:

```typescript
// ❌ 差:系统视角,模型无从判断何时该用
description: "调用售后中台工单查询接口 /api/v1/tickets/query"

// ✅ 好:任务视角,说清何时用、怎么用、边界在哪
description: "按售后单号查询售后单当前进度(审核/维修/退款/完结)。
  单号格式 T-YYYY-NNNN。查物流轨迹用 logistics 域工具,不要用本工具。"
```

差 vs 好的三条来源:**任务语义而非系统语义**(说"做什么",不说"调哪个接口")、**边界声明**(什么情况不该用我——防误选)、**格式示例**(给模型一个可模仿的填参样例)。工具多了之后还要加**域前缀命名**:`after_sales_query_ticket`,为第 6 章规模化立规。

`title` 也不可省——它是给**人**看的(工具目录、审批界面),description 是给**模型**看的,受众不同,都写。

## 5.3 错误处理:让模型能自纠

**关键实证(v2.4.0)**:工具处理器 throw 的异常,协议层返回的是**正常 result + `isError: true`**,错误消息进 content——不是 JSON-RPC error:

```json
{"result":{"content":[{"type":"text",
  "text":"单号 bad-123 不符合格式 T-YYYY-NNNN,请向用户确认后重试"}],
  "isError":true},"jsonrpc":"2.0","id":2}
```

这个区分是设计出来的,两类错误走两条路:

| | 业务层错误(可自纠) | 协议层错误(不可自纠) |
| --- | --- | --- |
| 例子 | 参数格式错、单号不存在、库存不足 | Server 崩了、方法不存在、网络断 |
| 返回 | `result` + `isError: true` + **给模型看的消息** | JSON-RPC `error` 对象 |
| 模型行为 | 读消息 → 修正参数 → 重试 | 放弃或上报人工 |

写错误消息的手艺:**写给模型看,不是写给日志看**。含三个要素——错了什么、为什么、模型下一步该做什么。对比:`"Error: code 40012"`(模型只能瞎猜)vs `"单号 bad-123 不符合格式 T-YYYY-NNNN,请向用户确认后重试"`(模型立刻知道怎么办)。

重试语义配套:**可重试错误**(超时、限流)在消息里说明可重试;**不可重试错误**(参数错)明确说"不要原样重试,先修正"。限流类错误附上重试间隔。

## 5.4 大结果:分页、截断与资源引用

工具结果直接进模型上下文,一个大结果就是一次上下文爆炸:

1. **服务端分页**:列表类工具强制 `page` / `page_size`,默认页大小给小值(10-20)。宁可模型多翻一页,不要一次灌两万条订单。
2. **字段裁剪**:返回模型需要的字段,不是接口返回的全部字段。`structuredContent`(v2.4.0 实测:handler 返回 `structuredContent` 会与 `content` 并存)配合 `outputSchema`,是"给模型的 JSON"与"给人看的摘要"分离的落点。
3. **资源引用**:超大内容(对账单 PDF、完整日志)不进结果——存为 resource,结果里给引用,模型/用户按需 `resources/read`。

## 5.5 幂等性:重试风暴的护堤

模型自纠意味着**重试是常态**。有副作用的工具(创建售后单)不幂等,一次用户确认可能产生三张单子。两条铁律:

1. **幂等键**:创建类工具收一个 client 生成的幂等键参数,Server 侧去重。
2. **先查后写**:能组合的先给查询工具,让模型确认不存在再创建——流程上消重。

## 5.6 工具评估:从上线第一天开始

描述改一个词,模型选工具的行为就可能回归。上线即埋点:每次 `tools/call` 记录(工具名、参数、是否 isError、模型重试了几次),聚合出**参数命中率、失败率、重试率**三个基础指标——埋点与 trace 细节 → langfuse 书;有了指标,第 6 章的目录治理才有淘汰依据。

## 5.7 贯穿案例:售后域前三件套

用本章标准把 echo 占位换成真实工具(方法完整体现 6 接口 → 工具的聚合,完整版第 6 章):

| 工具 | 聚合的中台接口 | 关键设计点 |
| --- | --- | --- |
| `after_sales_query_ticket` | 单查询 + 进度轨迹(2 接口) | 正则约束单号;structuredContent 返回结构化进度 |
| `after_sales_create_ticket` | 校验 + 风控 + 创建(3 接口) | 幂等键;缺退款方式时 MRTR `input_required` 向用户收集(第 2 章) |
| `after_sales_estimate_refund` | 退款试算(1 接口) | 只读无副作用;description 声明"仅试算,不产生退款" |

每一步:先写差版描述 → 观察误选/漏选 → 改成好版对照。这个对照过程本身就是团队评审工具定义的标准动作。

## 5.8 小结

- schema 是约束层(执行),description 是劝说层(选择)——两层都写满
- 业务错误走 `isError`,消息写给模型看:错了什么、为什么、下一步
- 大结果分页裁剪,大内容转 resource 引用
- 有副作用必幂等;上线即埋点

→ **第 6 章**把这些单工具的手艺,放大到数千接口的中台。
