# 第 6 章 规模化:业务中台的 MCP 化

> **初稿状态(2026-10-24)**:方法论为本书立场(依据第 2/5 章的协议与工具手艺 + 中台工程常识);涉及外部产品的形态与数据处标注[待核实],动笔完善时以当时市场现况与官方文档为准。

前两章的手艺都是"单个工具"级别的。现在放大尺度:你的业务中台有**数千个 REST 接口**,订单、物流、商品、售后、结算……每个 Agent 项目都在重复封装。这一章回答那个最常被问错的问题——

> "数千个接口怎么通过 MCP 暴露?"

**错误答案:暴露数千个工具。** 模型的工具选择准确率随工具数增长而下降(选择空间越大,描述相近的工具越容易混淆);每个工具的 schema 都占上下文预算,数千个工具还没开始干活,窗口先爆了;工具质量的维护成本线性上涨,没人维护得起。

正确答案是一条工程化路径:**聚合、生成、拆分、检索**。逐个展开。

## 6.1 接口 ≠ 工具:任务粒度聚合

中台接口是按**系统资源**切的(REST 风格:资源 CRUD),Agent 需要的是按**任务语义**的工具。两者之间存在一次翻译,这是本章最重要的一张表:

| 聚合模式 | 何时用 | 例子(贯穿案例) |
| --- | --- | --- |
| N 接口 → 1 工具(纵向聚合) | 一个用户任务背后固定的一串调用 | `after_sales_create_ticket` = 校验 + 风控 + 创建(3 接口)——原子任务不拆给模型,Server 侧编排 |
| 1 接口 → 1 工具(直通) | 接口本身就是完整任务语义 | `after_sales_query_ticket` 恰好对应单查询接口 |
| 1 接口 → 不暴露(裁剪) | 纯系统内部接口、无 Agent 任务语义 | 批量对账导入、内部缓存刷新 |
| M 接口 → 1 工具 + 参数(横切归并) | 同一任务的多个变体接口 | 按 region/渠道拆的 4 个查询接口 → 1 个带 `region` 参数的工具 |

判定口诀:**模型需要"决定"的才做成参数,模型不需要知道的都收进 Server**。工具数量由任务词汇表决定(一个业务域通常 5-15 个任务),不由接口数量决定——数千接口的售后/物流/商品各域,落下来通常是**每域个位数的工具**。

## 6.2 自动化生成管线:OpenAPI 是你的起跑线

手工写几千个工具定义不现实,而中台几乎都有 OpenAPI/Swagger 资产——生成管线让它变成起点而非终点:

```
OpenAPI 文档(资产)
   │  ① 解析:操作、参数 schema、描述
   ▼
候选工具清单(自动)
   │  ② 人工评审:聚合分组(6.1)、裁剪、命名归一
   ▼
工具定义(评审后)
   │  ③ 描述精修:任务语义重写、边界声明、格式示例(第 5 章标准)
   ▼
注册进域 Server
```

三个工程要点:

1. **生成的是"候选",不是"成品"**。自动生成解决 schema 与结构,但 description 的任务语义重写无法自动化——**描述精修是人工环节**,也是质量所在。省略这一步的团队会得到"数量达标、模型不爱用"的工具集。
2. **管线要幂等可重跑**:OpenAPI 变更 → 重新生成候选 → diff 出"接口变更影响的工具"清单——这个 diff 同时就是第 6.6 节变更管理的输入。
3. **绑定消费端做验证**:生成后立即用真实 Agent 冒烟(第 7 章的框架矩阵挑一个),命中率不达标的工具打回精修。

## 6.3 域拆分 + Gateway:拓扑设计

```
                 ┌────────────────────┐
   Host(Agent)──▶│   MCP Gateway      │◀── header 路由(2026-07-28)
                 │ 鉴权/租户/目录/限流  │
                 └─┬─────┬─────┬─────┘
              ┌────▼┐ ┌──▼──┐ ┌▼─────┐
              │售后域│ │物流域│ │商品域 │   ← 每域一个 Server
              │Server│ │Server│ │Server│      按域独立迭代/部署
              └──────┘ └─────┘ └──────┘
                    ▼ 中台 REST 接口群
```

- **按业务域拆 Server**,不做"一个巨无霸 Server":域是天然的迭代与责任边界(与中台团队组织结构对齐),故障隔离,工具目录清晰。
- **Gateway 是治理点,不是业务点**:统一鉴权与租户识别、工具目录聚合(6.5)、限流与审计、版本路由(第 3 章的 legacy 兼容可以收敛在 Gateway 一处)。2026-07-28 的无状态 + header 路由让 Gateway 不再需要会话亲和——这层在 2026 规范下才真正"薄得起来"。
- 网关产品(自建或 AWS AgentCore Gateway 之类的托管形态)[待核实:动笔时以市场现况为准]——选型判断标准写死三条:多租户工具可见性、按域路由、对 legacy client 的收敛兼容。

## 6.4 工具检索与动态发现:过载的最终解

域内工具数控制住了,但 Host 侧仍可能挂多个域——工具总数仍会涨。分层解法,按需启用:

1. **按角色挂载**:客服 Agent 只挂售后+物流域,运营 Agent 挂商品+结算域。目录治理(6.6)给出"角色 → 域"映射,这是成本最低、优先做的一层。
2. **分页发现**:`tools/list` 的分页游标,让 client 按"目录页"拉取,而不是一次性全量。
3. **search + load 模式**:工具数量真正大时,暴露一个 `search_tools` 元工具(按任务描述检索),模型先搜、再对选中的工具 `load` 详情、然后调用。两跳换来了"上下文里只有 1 个工具,背后是全部目录"。行业里 Anthropic 的 tool search、程序化工具调用等实践即此模式[待核实:以官方文档为准]。
4. **动态目录**:工具目录变更时经 `tools/list_changed` 通知 client 刷新(TS SDK 实测可见 capabilities 中的 `tools.listChanged: true`)——目录是活的,不是发版才变。

## 6.5 目录治理:让规模化可持续

工具多了以后,治理问题会反噬技术问题。四件套:

- **命名规范全域强制**:`domain_action`(`after_sales_create_ticket`),域前缀即路由与归属。
- **工具目录(Directory)**:每个工具一行——域、负责人、聚合了哪些接口、版本、状态(live/deprecated)。第 5.7 节的表就是它的雏形;没有目录,半年后没人说得清"这个工具动不得还是能改"。
- **变更管理**:描述与 schema 的修改走评审(它们直接改变模型行为);**破坏性变更新增工具名而非原地改**(工具名即 API,client 按名调用);OpenAPI diff(6.2)驱动影响面清单。
- **质量例行化**:第 5.6 的三指标(命中率/失败率/重试率)按月出报表,连续垫底的工具走"精修或下线"流程。

## 6.6 贯穿案例完整复盘

售后域从 0 到 1 的全过程,即本章方法的走查:

| 步骤 | 动作 | 产出 |
| --- | --- | --- |
| ① 输入 | 售后域 OpenAPI(20 接口) | 候选清单 |
| ② 聚合评审 | 任务词汇表讨论:售后单生命周期中模型真正要"决定"的事 | **6 个任务级工具**(查询/创建/试算/撤销/催办/评价),3 接口被裁剪,8 接口被纵向聚合 |
| ③ 生成+精修 | 管线生成 schema 初稿;描述逐个任务语义重写 | 工具定义 + 目录条目 |
| ④ 域 Server | mcp-core(TS 侧 v2)实现,Gateway 后注册 | `after-sales` 域上线 |
| ⑤ 消费验证 | agentscope-java Agent + 前端双端冒烟(第 7 章) | 命中率达标,发布 |

20 接口 → 6 工具:**压缩比 3:1 起步,且每个工具都是模型能准确选中的粒度**。把这个走查套到物流域、商品域,就是数千接口的全部真相。

## 6.7 小结

- 工具数由任务词汇表决定,不由接口数决定;聚合、裁剪、归并是常态
- OpenAPI 管线生成候选,描述精修是人工质量关
- 域 Server + Gateway,无状态规范让这层拓扑第一次"薄得起来"
- 过载解法分层上:角色挂载 → 分页 → search+load
- 目录四件套(命名/目录/变更/质量)让规模化可持续

→ **第 7 章**把这个 Server 挂给真正的多框架消费端,验证"一次封装,处处调用"。
