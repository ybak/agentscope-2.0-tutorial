# 第 1 章 初识 MCP

> **初稿状态(2026-10-24)**:全书最后写成的一章——现在全书已就位,引子如实领路。

中台团队都见过这个场景:客服 Agent 项目要接售后接口,封装一遍;前端 CopilotKit 要展示售后进度,再封装一遍;新起的数据脚本,又一遍。三个项目、三套鉴权、三份参数文档,同一个"查售后单"。**每套 Agent 框架 × 每个内部系统 = 一次重复封装**——这就是 N×M 集成爆炸。

Model Context Protocol(MCP)的答案是把 M 收敛到 1:中台把能力按协议暴露**一次**,所有 Agent 框架作为标准消费者接入。N×M 变成 N+M。

## 1.1 MCP 是什么、不是什么

**是什么**:一个开放协议,规范了"AI 应用(Host)如何发现并调用外部能力(Server)"——用 JSON-RPC 承载,把工具(tools)、资源(resources)、提示(prompts)三类能力标准化描述,让"模型看到什么、怎么调、结果什么形态"全部有协议约定。

**不是什么**:

- **不是模型能力**:MCP 不改变模型,它改变模型**能看见什么**——工具选择依然是模型+描述质量的博弈(第 5 章的主战场)
- **不是 RPC 框架**:JSON-RPC 只是载体;MCP 的价值在能力描述、发现与调用的**语义约定**
- **不是免写代码**:它消灭的是"每个框架重复封装"的那份代码,协议本身的工程(建模、描述、治理)是新的、更值钱的工作(第 6 章)

与近亲的边界:**function calling** 是模型厂商的 API 能力(单点、模型绑定);**OpenAPI** 描述系统接口(资源语义、面向人);MCP 站在它们之上,给 Agent 世界一个**任务语义的工具层**。

## 1.2 生态一瞥

- **官方 SDK**:TypeScript(v2.x)、Java(mcp-core 2.0.x)、Python 等,按对 2026-07-28 规范的支持度分级(第 4 章选型表)
- **Server 生态**:GitHub 等大型服务已原生提供 2026-07-28 MCP 端点;企业内部则以自建域 Server 为主(第 6 章)
- **框架支持**:agentscope-java、ragflow、CopilotKit、主流 AI CLI 均以 client/Host 身份接入——支持矩阵见第 7 章
- **规范演进**:2024-11-05 起五版,当前 **2026-07-28**(无状态核心)——选教程、选 SDK 先看协议版本(第 3 章)

## 1.3 本书怎么读

全书围绕一个贯穿案例:**中台售后域,20 个 REST 接口 → 6 个任务级工具 → Gateway → 多框架消费**。

| 你是 | 路线 |
| --- | --- |
| Server 实现者(后端,主线) | 顺序通读:第 2 章概念 → 第 4 章上手 → 第 5 章工具手艺 → 第 6 章规模化 → 第 8 章上生产 |
| Client 集成者 | 第 2 章 + 第 4 章 + **第 7 章**(框架矩阵与双端实测),细节回各自框架书 |
| 平台/架构决策 | 第 1 章 → 第 6 章 → 第 3 章(版本策略)→ 第 8 章(安全基线)→ **第 9 章**(路线图与立项) |
| 测试/运营 | 第 2.3 节(能力边界)+ 第 5.6 节(工具指标)+ 第 6.5 节(目录治理) |

写作约定:所有代码在指定 SDK 版本下实测或明确标注"未实测"(每章附实测清单);外部事实标注核实日期;与书架其他书的分工——框架 API 细节一律交叉引用,本书只拥有协议与规模化方法论。
